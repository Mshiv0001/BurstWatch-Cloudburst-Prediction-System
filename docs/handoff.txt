## Architecture: Subscriber System

```
User                Frontend                Backend                Storage
 |                     |                       |                      |
 | Enter email         |                       |                      |
 |-------------------->|                       |                      |
 |                     | POST /subscribers/subscribe                  |
 |                     |---------------------->|                      |
 |                     |                       | Generate OTP         |
 |                     |                       | Send email via SMTP  |
 |                     |                       |                      |
 | Enter OTP           |                       |                      |
 |-------------------->|                       |                      |
 |                     | POST /subscribers/verify-otp                 |
 |                     |---------------------->|                      |
 |                     |                       | Verify OTP           |
 |                     |                       | (brute-force check)  |
 |                     |                       | Create JWT           |
 |                     |<-- JWT token ---------|                      |
 |                     |                       |                      |
 | Google Sign-In      |                       |                      |
 |-------------------->|                       |                      |
 |                     | POST /subscribers/google-auth                |
 |                     |---------------------->|                      |
 |                     |                       | Verify Google ID token
 |                     |                       | (google-auth library)|
 |                     |                       | Skip OTP, create JWT |
 |                     |<-- JWT token ---------|                      |
```

**JWT payload:** `{ "sub": "<email>", "exp": <unix timestamp> }`  
**Secret:** `JWT_SECRET` env var (see env vars section below)  
**Brute-force limit:** Configurable — after N failed OTP attempts within a window, that email is locked out.

## Architecture: Multi-Layer Cache (`src/cache/`)

The frontend cache system is layered as follows:

```
Request
   |
   v
Memory Cache (in-process Map, TTL-based)
   | miss
   v
SessionStorage Cache (tab-scoped, survives soft refreshes)
   | miss
   v
IndexedDB Cache (persistent, survives hard refreshes)
   | miss
   v
Network fetch (API / external service)
   |
   v
Populate all cache layers on response
```

Key files in `src/cache/`:
- `cacheManager.js` — orchestrates all layers, TTL enforcement, cache-key namespacing
- `memoryCache.js` — in-process Map with TTL
- `sessionCache.js` — SessionStorage adapter
- `idbCache.js` — IndexedDB adapter (async)
- `cacheConfig.js` — per-data-type TTL configuration (weather data, terrain, predictions, etc.)

All 6 fail with:
```
AttributeError: 'Session' object has no attribute 'headers'
```

Root cause: The test fixture creates a mock `Session` object that does not have a `.headers` attribute. `weather.py` calls `self.session.headers.update(...)`.

A guard was added to `weather.py`:
```python
if hasattr(self.session, "headers") and hasattr(self.session.headers, "update"):
    self.session.headers.update(...)
```

However the pipeline tests still fail because the mock `Session` itself does not set `.headers` to a dict-like object. The fix requires updating the mock fixture in `test_pipeline.py` to add `session.headers = {}` (or use `unittest.mock.MagicMock()` which auto-creates attributes).

## Network Quirk: IPv4 to GitHub Blocked

**Problem:** Direct IPv4 connections to `github.com:443` fail at the local gateway (`192.168.29.1` returns ICMP "Destination net unreachable"). IPv6 is fully functional on this machine.

**Root cause:** GitHub has no native `AAAA` DNS records. The gateway blocks outbound IPv4 to external IPs.

**Workaround used:** A local NAT64 HTTP CONNECT proxy that resolves GitHub hostnames via a DNS64 resolver (`2a00:1098:2b::1`) which synthesizes IPv6 addresses for IPv4-only targets, then opens the TCP connection over IPv6.

**Proxy file location:**
```
C:\Users\mshiv\.gemini\antigravity\brain\2dc0395e-e00e-4f5a-b497-bb53c6f61c82\scratch\nat64_proxy.py
```

## Phase 21 — Open-Meteo 429 Quota Resilience (QuotaShield™) — PLANNED, NOT YET EXECUTED

> **Status:** Plans written at `.gsd/phases/21/`. Not yet executed. Run `/execute 21` to implement.

### Root Cause of the 429 Problem

The backend calls Open-Meteo on **every** `/predict/location` request with no caching. The Rain Tracker scans all **419 cities** at once on panel open, burning 419 API requests in seconds. Open-Meteo free tier allows ~10,000 requests/day (~7 req/min sustained). With frequent user interactions, the quota is exhausted, causing HTTP 429, which the backend raises immediately as a hard error — turning the ML status indicator red in the UI.

**Polling cadence in `App.jsx`:** `REASSESS_INTERVAL_MS = 20 * 60 * 1000` (every 20 min per selected station). The 429 is not from the interval — it's from Rain Tracker batch scans and manual station clicks all hitting Open-Meteo without any cache.

### The Fix: 15-Minute Prediction Cache (Your Suggestion)

Cache the **full ML prediction result** (not just the weather DataFrame) keyed by `(lat, lon)` with a **15-minute TTL**, at the service layer in the backend. Open-Meteo forecasts only refresh every 15 minutes, so this is scientifically correct — you never serve data more stale than what a fresh call would return.

```
Request → check prediction_cache(lat, lon, 15-min TTL)
  ├─ HIT  → return {risk_percent, label, confidence, stale: false}  ← 0 API calls
  └─ MISS → fetch Open-Meteo → run ML → cache 15 min → return
```

### Resource Savings

| Metric | Without Cache | With 15-min Prediction Cache |
|---|---|---|
| Rain Tracker scan (419 cities) | 419 Open-Meteo requests | 0–28 (only expired entries) |
| Repeated station clicks | 1 request each | 0 (cache hit) |
| ML inference per click | ~80–150ms CPU | 0ms (dict lookup) |
| Rain Tracker CPU (419 cities) | ~42 sec ML inference | ~0 sec |
| Daily API requests (1 user) | ~2,500–5,000/day | ~100–200/day |
| Free tier headroom (10k/day) | 50–75% consumed | **98–99% free** |

**~95% reduction in both Open-Meteo API calls and ML inference CPU.**
